# hotsrm 体系文件（管理制度）模板

> 状态：v0.3（2026-10-23）。生成脚本、参数文件首版和 12 份核心模板（QP-01、QP-02、ZC-01～ZC-03、SP-01、GL-01、GL-02、GL-04、GL-05、WI-01）已完成；
> 其余模板按 §6 的计划随核心版本补齐。审批权限以核心设计 03 §12 的审批矩阵为唯一来源，ZC-02 等按它编写（2026-10-23，P-D1）。
> 模板代号、名称和编写状态以 [`templates/index.yaml`](./templates/index.yaml) 为准。

## 1. 为什么要有体系文件模板

客户上 SRM 时，通常会要求先把供应商管理制度定下来，再按制度配置系统。如果制度和
系统各写各的，很快就会出现「制度说 3 天、系统配 5 天」「制度要求双人复核、系统只有
一级审批」这样的不一致，内审和外审都会开不符合项。

hotsrm 把管理制度和系统放在一起维护：

- **每条控制要求对应一个系统控制点**：制度里写「在 SRM 系统中执行」的要求，系统一定
  有对应的控制；系统里的每个强制控制，也都能在制度里找到条款依据；
- **参数只维护一处**：审批金额档、整改时限、绩效等级线、证书提醒天数等，写在一份参数
  文件里，同时用于生成制度文本和配置系统；
- **模板通用、实例私有**：本仓库只放通用模板和示例参数；某个客户的参数取值、部门
  名称、文件编号、样式模板和专属段落，放在该客户的私有仓库里。

## 2. 文件层级

| 层级 | 类型 | 说明 |
|---|---|---|
| 政策 | 采购与供应商管理政策、采购授权审批表、风险控制矩阵 | 管理层批准；规定原则、管理架构、审批权限和主要风险的控制，下层文件依据它制定 |
| 对外 | 供应商行为准则、供应商手册 | 面向供应商公开或随合同提供，只写对供应商的要求 |
| 一级 | 质量手册（管理手册） | 客户已有，不由 hotsrm 提供；在「外部提供的过程、产品和服务的控制」相关章节引用二级文件 |
| 二级 | 程序文件 | 规定过程的职责、程序和控制要求 |
| 三级 | 管理办法 / 作业指导书 | 规定具体业务的方法、标准和参数 |
| 四级 | 记录表单 | 与系统单据一一对应；系统上线后以系统记录为准 |

## 4. 模板与参数的格式

模板正文用 Markdown 编写。参数文件放在仓库根目录的 `params/`，因为应用包构建时也要
读它（见 [ADR-0005](../docs/adr/0005-governance-and-system-share-parameters.md)）：

```
params/                           参数定义与示例默认值（制度与系统共用）
├── core.yaml
├── bulk.yaml
├── hazmat.yaml
└── soe.yaml

governance/
├── README.md                     本文
├── org.example.yaml              组织信息示例（客户未提供时使用）
├── templates/
│   ├── index.yaml                模板与表单登记表：代号、名称、所属、编写状态
│   ├── core/                     QP-01 … GL-10
│   ├── bulk/                     BK-01 … BK-03
│   ├── hazmat/                   HZ-01 … HZ-03
│   └── soe/                      SO-01 … SO-05
└── scripts/
    ├── build.py                  渲染模板 → Markdown → Word；生成待确认事项清单与参数表
    └── filters.lua               Word 版式（条款、列项、表格后的段落）
```

### 4.1 模板标记

| 标记 | 含义 | 示例 |
|---|---|---|
| `{{param.<键>}}` | 参数值；值为键值表时用 `{{param.<键>.<子键>}}` | 在 `{{param.scar_containment_hours}}` 小时内提交临时措施 |
| `{{org.<键>}}` | 客户的组织信息（键见 `org.example.yaml`） | `{{org.company_name}}`、`{{org.dept.procurement}}` |
| `{{doc.<代号>}}` | 引用另一份文件，生成「编号《名称》」；`.title` 只要《名称》，`.number` 只要编号 | `{{doc.QP-02}}`、`{{doc.GL-06.title}}`、`{{doc.QR-01.number}}` |
| `<!-- pack:<包> -->` … `<!-- /pack -->` | 只在组合了该扩展包时保留；可写在段落内，也可独占一行包住几段 | `<!-- pack:bulk -->…<!-- /pack -->` |
| 行尾的 `<!-- pack:<包> -->` | 只在组合了该扩展包时保留这一行；用于表格行和列表项 | `\| 危险货物道路运输 \| … \| <!-- pack:hazmat -->` |
| `<!-- block:<名称> -->` … `<!-- /block -->` | 客户可以整段替换的段落，默认内容可以为空 | `<!-- block:duties-note -->` |

扩展包条件写 `bulk`、`hazmat`、`soe`；`a,b` 表示任一组合即保留，`!bulk` 表示未组合时
保留（用于给出不组合扩展包时的替代表述）。条件块不能嵌套；条件段落里的条款放在
所在小节的末尾，避免去掉后编号断档。一个小节里只能有一个扩展包的独立条款放在末尾；
同一小节还有其他扩展包的内容时，并入相关的通用条款（写成条款内的条件句），不单独编号。

其他约定：

- 条款编号与正文之间用全角空格「　」，如 `6.1.1　…`；生成 Word 时这类段落顶格排版；
- 列项用 `a)`、`b)`，项之间空一行；无序列表生成为逐行排列的段落；
- 表格的列宽按分隔行 `|----|--------|` 中短横线的数量分配；
- 正文里需要客户确认的地方由客户实例标注（见 §5），模板本身不写【待确认】。
- 模板按中国法规编写、对标国际框架（[ADR-0007](../docs/adr/0007-china-first-with-overseas-seams.md)）：法规和标准的名称集中
  列在「引用文件」一章（没有这一章的文件，如政策层、对外文件和按「总则」体例编写的办法，只写法规领域、不写法规全称），条款只写要求；资质名称放资质清单，条款写「按资质清单」。

### 4.2 参数定义

参数定义的每一项包括：键、中文名、单位、示例默认值、使用它的文件与条款、对应的系统
配置位置，以及可选的渲染格式。`system` 写「制度要求」的参数只进制度文本，系统不强制、
也不要求在应用包里配置；写了系统位置的参数，应用包配置必须取同一个值。例如：

```yaml
scar_containment_hours:
  label: 整改临时措施提交时限
  unit: 小时
  example: 72
  used_in: [QP-01 6.8.2, GL-07]
  system: srm_quality_issue.containment_due 的计算规则（核心 03 §8）

cert_reminder_days:
  label: 资质证书到期提醒
  example: [30, 15, 7]
  format: "{} 日"                 # 列表逐项套用后用「、」连接：30 日、15 日、7 日
  ...
```

## 5. 客户实例与生成方式

客户的私有仓库只放与 hotsrm 不同的部分。它同时负责组合客户的系统发行版和生成客户的
体系文件（发行版的组合方式见 [ADR-0002](../docs/adr/0002-packs-composed-into-one-app.md)）：

```
hotsrm-<客户>/
├── hotsrm.lock                 生成所用的 hotsrm 版本（提交号）
├── build.sh                    调用 hotsrm 的 governance/scripts/build.py
├── objectstack.config.ts       组合：核心 + 选定扩展包 + 客户初始化数据（开始开发后建立）
├── objectstack.manifest.json   客户发行版的标识，只发布到客户自己的组织
├── data/                       品类、物资分类目录、资质清单、组织结构等初始化数据
└── governance/
    ├── org.yaml                公司名称、部门名称、称谓、物资分类的典型物资
    ├── params.yaml             参数取值：confirmed 已确认，pending 待确认（标黄）
    ├── packs.yaml              组合的扩展包（与 objectstack.config.ts 一致）
    ├── documents.yaml          文件登记：模板代号 → 客户文件编号与名称；版本、状态、修订记录
    ├── pending.yaml            正文中的待确认标注：在指定文字后插入【待确认：说明】
    ├── overrides/<代号>/       替换模板中的 block 段落（尽量少）
    ├── documents/              客户专属文件（不来自模板），如体系文件架构清单
    ├── reference.docx          客户的 Word 样式模板（可选；没有就用 hotsrm 的默认版式）
    └── build/                  生成的 Word 与 Markdown（不提交）
```

生成命令（在客户仓库中）：

```bash
python3 <hotsrm>/governance/scripts/build.py --instance governance          # 生成
python3 <hotsrm>/governance/scripts/build.py --instance governance --check  # 只检查
```

不带 `--instance` 时用示例组织和示例参数生成标准版，`--packs bulk,hazmat` 指定组合的
扩展包。脚本会检查：参数和文件代号都已定义、引用的扩展包文件已组合、覆盖文件都有对应
的 block、待确认标注的定位文字正好出现一次、没有残留的标记。

每次生成得到：

| 输出 | 说明 |
|---|---|
| 每份文件的 `.docx` 与 `.md` | 封面（公司名、文件名、文件控制表、修订记录）、页眉页脚由脚本填入 |
| 待确认事项清单 | 待确认的参数和正文标注，发给客户逐项确认 |
| 参数表 | 全部参数的取值、状态（已确认 / 待确认 / 默认）和对应的系统位置，用于配置系统 |

生成与评审流程：

1. 用 hotsrm 模板 + 客户的 org、params、packs、documents、pending、overrides 生成 Markdown，
   再用 pandoc 转成 Word；客户提供了 `reference.docx` 就按它的样式排版，页眉中的
   `{{header_left}}`、`{{header_right}}` 由脚本替换为公司名和文件名；
2. 把 Word 和待确认事项清单发给客户，客户在 Word 里批注或修订，不需要学习 git；
3. 实施顾问把意见合并回源文件（参数从 pending 移到 confirmed、删掉已确认的标注），
   重新生成；
4. 定稿后客户签批，**受控版本是签批后的 PDF 或 Word**，由客户的文件控制体系保存；以后
   修订仍改源文件，每次修订对应一次提交；
5. 参数文件中的取值同时用于配置客户环境里的 SRM，保证制度与系统一致。
