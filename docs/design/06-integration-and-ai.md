# 06 · 集成与 AI

> 所属：[SRM 设计总览](./README.md)　·　上一篇：[05 界面与分析](./05-experience-and-analytics.md)　·　下一篇：[07 交付计划](./07-delivery-plan.md)

## 1. ERP 集成

### 1.1 原则

1. **记账系统唯一**：物料、订单记账、收货、应付、付款以 ERP 为准；供应商生命周期、
   寻源、价格、协同过程数据以 SRM 为准。一个字段只有一个「主人」（§1.3）。
2. **入站幂等**：ERP 写入 SRM 一律走批量 API 的 `upsert`，按 `erp_*_id` 匹配。重复
   消息、乱序重放都不会产生重复单据。
3. **出站可补偿**：SRM 推 ERP 的每类数据（I3、I5、I6、I7、I10、I11、I14），在源记录上
   带三个同步字段（对象清单见 [02 §1](./02-domain-model.md#1-建模原则) 第 8 条）——
   `erp_sync_status`（`pending` / `synced` / `failed`）、`erp_sync_error`、
   `erp_synced_at`。推送失败只改状态、不回滚业务；追赶式扫描 flow 定时重推
   `pending` / `failed` 的记录（`srm_erp_push_retry`），「同步失败」列表视图给管理员人工处理。
4. **集成用专用服务账号**：ERP 侧使用平台 API 密钥对应的集成账号，挂权限集
   `srm_integration`，只授予集成所需对象的读写，不授予报价单、银行账号等敏感数据（见 [04 §2.2](./04-security-and-portal.md#22-权限集)）。
5. **有中间件就走中间件**：企业已有 ESB / iPaaS 时，映射、重试、监控放在中间件，
   SRM 只暴露标准 API 与 webhook；没有中间件时用上面第 3 条的同步字段兜底。

### 1.3 字段归属

| 对象 | ERP 拥有（SRM 只读） | SRM 拥有 |
|---|---|---|
| 物料 | 全部字段 | — |
| 供应商 | `erp_vendor_code`、ERP 侧冻结状态 | 其余全部（档案、状态、等级、资质） |
| 采购订单 / 行 | 订单号、物料、数量、单价、需求日期、行状态（关闭 / 取消） | 供应商答复交期与数量、延期原因、交期风险、确认时间 |
| 收货 / 检验 | 全部字段 | `on_time`、`amount`、`reconciled`（SRM 计算） |
| 发票 | 应付凭证号、付款金额与日期 | 发票信息、查验结果 |

### 1.4 与主流 ERP 的对照

接口名为各 ERP 常见的标准做法，具体以企业 ERP 版本与已有接口为准。

| SRM 数据 | SAP（ECC / S/4HANA） | 用友（U9 / NC 等） | 金蝶（云星空等） |
|---|---|---|---|
| 供应商 | 供应商主数据（S/4 为业务伙伴）；IDoc `CREMAS` 或 API | 供应商档案 | 供应商 |
| 银行账户 | 供应商银行信息 | 供应商银行账户 | 供应商银行信息 |
| 价格信息记录 | 采购信息记录；IDoc `INFREC` | 价目表 | 采购价目表 |
| 采购订单 | 采购订单；IDoc `ORDERS` / `ORDCHG` | 采购订单 | 采购订单 |
| 订单确认 | 订单确认；IDoc `ORDRSP` | 采购订单回复 / 交期 | 采购订单交货明细 |
| 送货通知 | 内向交货；IDoc `DESADV` | 到货单 | 收料通知单 |
| 收货 | 物料凭证（收货 / 退货） | 采购入库单 | 采购入库单 / 退料单 |
| 检验 | 检验批 | 来料检验单 | 检验单 |
| 发票 | 发票校验；IDoc `INVOIC` | 采购发票 / 应付单 | 采购发票 / 应付单 |
| 付款 | 付款凭证 | 付款单 | 付款单 |

### 1.5 接口形态

- **入站**：平台 REST API 的批量操作支持 `upsert`（按外部编号匹配），ERP 或中间件
  直接调用；需要 SRM 内后续动作的，由对象上的 record_change flow 接着处理（例如收货
  写入后判定准时）。
- **出站**：flow 的 `http` 节点调用 ERP 或中间件接口，凭据以平台的密钥 / 连接器机制
  保存，不写进 flow 定义；或用 webhook 把事件推给中间件订阅。
- **回调**：电子签、付款等异步结果通过 `api` 类型的 flow 接收。

## 2. 外部服务

| 服务 | 用途 | 接入点 | 期次 |
|---|---|---|---|
| 企业信息服务（工商、司法、经营异常） | 注册时核对名称与信用代码；每周风险扫描 | `http` 节点，按批调用 | 一期（核对），四期（扫描） |
| 电子签章 | 合同、质量协议、廉洁协议在线签署 | `http` 发起 + `api` 回调 | 二期 |
| 对公账户验证 | 银行账户真实性核验（四要素 / 小额打款） | `http` | 二期 |
| 发票查验 | 专票 / 数电票真伪与状态 | `http` | 四期 |
| 邮件 / 短信 | 通知 | 平台通知通道 | 一期 |

所有外部服务按「调用失败不阻断主流程」设计：失败时记录到业务字段，人工可重试或
转人工核验。

## 3. AI 助手

ObjectStack 的定位是**让 AI agent 安全执行真实业务**的后端：AI 调用的是带类型、带
权限、带审计的业务工具，而不是直接查库。SRM 是检验这个定位的好场景，因为它同时有
竞争对手隔离和封标两条硬边界。

### 3.1 治理前提

| 前提 | 平台机制 | 对 SRM 的意义 |
|---|---|---|
| AI 以提问者本人的身份调用工具 | 回答级权限控制，AI 不能成为越权通道 | 截止前问「这张询价单谁报价最低」得不到任何报价数据；供应商的 agent 只能看到本公司数据 |
| 写操作先预览、经人确认 | 修改类工具先返回待确认的变更卡片 | AI 起草的催办、评分、定标建议都需要人确认后才生效 |
| 每次工具调用可审计 | 企业版 AI 治理：记录谁问了什么、触达了哪些数据 | 寻源过程中的 AI 使用可被内控复盘 |
| 外部 agent 接入 | 环境的 agent 连接入口（MCP 兼容） | 供应商可用自己的 agent 以门户身份确认订单、回复交期 |

### 3.2 用例

| 用户 | 用例 | 读写 | 期次 |
|---|---|---|---|
| 采购员 | 「列出本周所有交期风险订单，按缺料紧急程度排序，并起草催办消息」 | 读订单行；起草通知（需确认） | 二期 |
| 寻源工程师 | 「为这张询价单推荐 5 家合格供应商，说明依据（等级、近期 OTD、价格竞争力）」 | 读名录与绩效 | 一期 |
| 评标小组 | 「开标后汇总比价，标出低于均价 30% 的异常报价和交期偏离」 | 读报价（开标后才有数据） | 一期 |
| SQE | 「汇总这家供应商近 4 个季度整改单的根因分类和重复问题」 | 读整改单 | 三期 |
| 品类经理 | 「对比上传的营业执照与申请表填写的信用代码、有效期是否一致」 | 读附件，需要文档识别能力，先做可行性验证 | 待评估 |
| 采购总监 | 「今年电子类物料的节约额是多少，比去年如何」 | 读寻源与价格数据 | 一期 |
| 供应商（外部 agent） | 「确认所有需求日期在两周以后的订单行，交期按需求日期答复」 | 写本公司订单行答复（需确认） | 二期 |

### 3.3 用 AI 搭建 SRM 本身

平台的 AI 搭建助手适合**原型验证**：用一句话描述某个模块（例如「供应商准入」），
它会先给出 3–5 个对象的方案，确认后生成对象、视图和应用外壳，便于业务方尽早
看到样子。但完整的 SRM 应以**代码仓里的应用包**为唯一事实来源：35 个对象、
二十多条 flow、精细的 RLS 需要版本管理、代码评审和回归测试。建议做法是用 AI 搭建
产出原型 → 业务确认 → 按本设计在应用包里正式实现。
