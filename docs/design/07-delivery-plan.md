## 2. 验收标准

### 2.1 门槛 1：内部 MVP（v0.5 出口）

按下面的剧本在内部工作台完整走一遍，不涉及门户和 ERP。

1. 品类经理为供应商 X 登记准入申请，选择「电子元器件」品类（A 类物资、高风险），上传
   营业执照；系统查重通过；
2. 采购主管（或品类经理）收齐 ISO9001 证书与银行账户（采购员对证书只读、看不到银行账户，04 §2）；应付会计核验银行账户；
3. SQE 完成现场审核并上传报告，审核通过；
4. 准入审批按矩阵走品类经理、采购总监两级，A 类加质量经理会签；审批人与发起人为同一人
   时自动改派；通过后 X 变为「合格」；
5. 导入上月交付记录表格两遍，结果一致；其中一条不合格记录开出整改单，X 的整改回复由
   SQE 代录（FR-602），SQE 审核退回一次后通过，验证关闭；
6. 月初考评 flow 为 X 生成本期考评单（A 类按月），OTD、合格率、PPM 与导入数据一致；
   采购总监审定发布；
7. X 的考评连续两期为 D 级：第一期发布后自动生成冻结处置单草稿，第二期改为生成淘汰处置单草稿
   （[03 §10](./03-processes-and-automation.md#10-p9-绩效评估v05) 第 6 步）；处置单审批通过后 X 不能再被关联新的合同；
8. 将 X 的 ISO9001 证书有效期改为昨天，次日扫描后 X 被标记「资质异常」，列表上有提示；
9. 为 X 新建合同，到期前 30 天提醒合同所有者、品类经理和采购员。

### 2.2 门槛 2：门户与寻源（v0.7 出口）

在 2.1 的基础上增加：

1. 品类经理邀请 X 的联系人加入门户；X 在门户补齐证书并回复一张整改单；X 看不到其他
   供应商的任何数据（[04 §3.7](./04-security-and-portal.md#37-隔离验收测试)）；
2. 寻源工程师建询价单（3 个物料），邀请 X、Y、Z 三家；截止前内部只能看到「已报价 N 家」；
   Y 在截止后尝试改价被拒绝；
3. 开标，比价矩阵显示三家价格；定标金额 50 万，走两级审批；通过后价格记录生成、旧价格
   被截断，三家收到结果通知。

### 2.3 量化标准

| 项 | 标准 | 门槛 |
|---|---|---|
| 导入幂等 | 物料、存量供应商、交付记录三张样例表格各跑两遍，结果一致 | 1 |
| 数据迁移 | 存量供应商、联系人、证书两轮迁移演练，抽检准确率 ≥ 99% | 1 |
| 审批矩阵 | [03 §12](./03-processes-and-automation.md#12-审批矩阵) 每一行各有一条通过用例，自审被拒一条 | 1 |
| 性能 | 01 §7 的列表视图响应时间达标 | 1 |
| 可用性 | 2 名采购员在无培训的情况下完成「登记申请 → 审批通过」 | 1 |
| 隔离测试 | 04 §3.7 全部用例通过，零例外 | 2 |
| 托管环境隔离复测 | §6.2 V6：托管环境下成员键隔离与 fail-closed（键为空、键不被识别）通过 | v0.6 出口 |
| 封标测试 | 截止前经界面、API、导出、仪表盘、AI 助手五个通道均取不到报价内容 | 2 |
| 可用性 | 5 家试点供应商在无培训的情况下完成「接受邀请 → 提交报价」 | 2 |

门槛 1 验收结果（2026-10-26，main 上的本地演示环境，`pnpm setup:local` 造数）：

- §2.1 九步剧本在浏览器里按岗位走通；第 8 步发现证书「必备资质」没有按品类自动标记、必备证书过期后供应商不进「资质异常」，
  第 9 步到期提醒没有发给采购员，均由 PR #70 修复后重跑通过；第 2、7、9 步的措辞按权限矩阵和 03 §10 校正。
- 导入幂等：物料、存量供应商、联系人、证书、合同与明细、交付记录各导入两遍，第二遍只更新、不新增，业务字段逐条一致。
- 数据迁移：存量供应商、联系人、证书在两个全新环境各演练一轮，逐格核对 164 / 164（100%）。
- 审批矩阵：本阶段适用的 10 行（准入两行、合同、银行账户、其他信息变更、冻结 / 解冻、淘汰、绩效发布、SCAR 审核）各有
  一条通过用例，另有一条「采购主管审批本人发起的变更单不计入、改由另一位采购主管」；寻源与定标 6 行随 v0.7 验收。
  第 4 步「审批人与发起人为同一人时自动改派」验收时发现准入审批没有做到（品类经理能初审本人发起的申请），
  按 03 §3 第 6 步补上：初审人就是发起人时品类经理一级上提采购总监（hotsrm#72），自动化测试覆盖标准与 A 类两种申请。
- 性能：供应商、交付记录各 10 万行时，列表首屏（含页面加载）1.1–1.5 秒，筛选视图同样在 2 秒内（单机 sqlite，
  正式环境上线前按部署数据库复测）。
- 可用性（2 名采购员无培训完成「登记申请 → 审批通过」）需要真实用户，留到试运行时做。

## 3. 应用包结构与工程规范

### 3.1 目录结构

核心的源码放在仓库的 `src/core/`（`type: app`，命名空间 `srm`）；现阶段只有核心，扩展包
目录和桥接模块在第一个包立项时再建（[ADR-0009](../adr/0009-core-first-pack-criteria-and-customer-layer.md)），
组合方式见仓库根目录的 [README](../../README.md) 与 [ADR-0002](../adr/0002-packs-composed-into-one-app.md)。

```
src/core/

├── objects/                     # 每个对象一个文件：supplier.object.ts …
```

### 3.2 规范

建模规范、分支与 PR、CI 门禁、测试策略、版本与升级，见 [docs/engineering](../engineering/README.md)。
要点：

- **契约优先**：元数据以 `@objectstack/spec` 为唯一契约，发布前跑平台 lint 与构建校验，
  校验报错一律改元数据，不在运行时打补丁；
- **环境**：开发、预发、生产三套环境，配置与元数据通过应用包版本推进，不在生产环境
  手工改元数据；
- **客户个性化放客户层**：参数、体系文件实例、Studio 覆盖层、客户私有包；不改核心源码。

## 4. 风险与应对

| # | 风险 | 可能性 | 影响 | 应对 |
|---|---|---|---|---|
| R1 | 门户用户可见的用户目录范围不满足隔离要求（04 §3.6） | 低：18.1.0 的组织角色 `external` 已修复（objectstack#25233） | 中：暴露竞争对手与员工联系方式 | 门户用户一律按 `external` 角色邀请，环境成员策略设 `invite-only`（04 §3.3）；V1 已通过（2026-11-02），隔离测试覆盖用户目录 |
| R2 | 同一环境其他应用的默认权限集把数据开放给供应商用户 | 低：`external` 成员不持 `everyone` 锚点，默认权限集不作用到他们（18.1.0） | 高 | V5 已实测通过（2026-11-02）；v0.6 上线前仍逐个审查环境内所有 `isDefault` 权限集，新应用上线纳入同一审查 |
| R3 | 定时任务延迟或漏跑（平台不提供保证，PF1） | 中 | 中：提醒延迟 | 追赶式扫描（03 §2.3）；强制规则不依赖计时器 |
| R4 | `runAs: 'system'` 的 flow 不得写岗位任命和邀请（objectstack#25251），开通门户有手工步骤 | 高 | 低：效率 | 2026-11-02 起门户按成员键隔离（ADR-0010），不再为每家供应商建岗位；开通由组织管理员操作（04 §3.3）：邀请在成员页发，静态岗位任命由 `runAs: 'user'` 的「开通门户」flow 写（V2、V3，2026-11-02） |
| R5 | 供应商不愿用门户，继续用邮件和微信 | 中 | 高：协同价值落空 | 试点选配合度高的供应商；邮件只给链接不给内容；在采购合同中约定门户为正式渠道 |
| R6 | 存量供应商数据质量差（重复、缺信用代码） | 高 | 中 | v0.2 导入前专项清洗；导入时按信用代码（境外按国家 / 地区 + 注册号）匹配，可重复执行；标记「存量导入」进「存量待复核」视图（[导入说明](../implementation/legacy-supplier-import.md)） |
| R7 | ERP 集成推迟后，交付数据靠每月导入，客户不按时导出则绩效断档 | 中 | 中 | 导入模板与操作清单写进实施手册；考评 flow 发现本期无交付记录时标记「数据不全」而不是给零分 |
| R8 | 每版对象与 flow 较多，回归成本上升 | 中 | 中 | 审批矩阵、导入幂等、关键 flow 的自动化测试进 CI（docs/engineering §3） |
| R9 | 考评在 flow 里批量处理，供应商多时运行时间长 | 低 | 中 | 按法人或品类错峰拆分；规模继续增长时评估服务端函数。2026-10-24 实测：200 家供应商 × 30 行交付记录一次生成约 8.6 秒、重跑约 0.6 秒（03 §10），暂不拆分；测试 `test/performance-generate-load.test.ts`（`SRM_LOAD_TEST=1`） |
| R10 | 审批人与发起人为同一人（职责分离失效） | 中 | 中 | 岗位分离 + `expression` 审批人改派（04 §6）；平台开关已在主干（PF5），发版后改用 |
| R11 | 客户落地时要求改核心字段，覆盖层与核心升级冲突（平台目前不检测，objectstack ADR-0005） | 中 | 中 | 客户层规则（ADR-0009 第 4 条）；核心升级前跑「核心 + 客户层」组合构建 |

18.3.0 带来的行为变化（2026-11-03 升级时发现，已按平台的新规则改）：

- `modifyAllRecords` 压过同一权限集上的字段级只读（lint 规则 `security-superuser-field-mask-inert`）。系统管理员删考评单原来靠它，
  升级后管理员能改分数；改为 `allowEdit` + `allowDelete` 加两条只对考评单的行级策略（删除、编辑），字段级权限全部只读照旧生效。
  考评单由系统生成、没有所有人，删除不能靠所有权或写深度。
- 记录上的文件字段只能引用调用人自己打开得了的文件（objectstack#25692）：上传人、文件挂着的记录可读，或系统身份写入。界面上传
  不受影响；测试里造文件时要写上传人（`test/support/files.ts`）。
- 以系统身份运行的 flow 从 trigger 入口带 `recordId` 启动时必须同时给 `objectName`（PF18 的修复），否则 400；测试改走
  `test/support/flows.ts`。
- 同一文件里匹配键相同的行都不写（PF16）：两份试导样例的结论随之改变，见[导入说明 §6](../implementation/legacy-supplier-import.md#6-试导结果与清洗清单)
  和[交付记录导入说明 §5](../implementation/delivery-import.md#5-试导结果与清洗清单)。
