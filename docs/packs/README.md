# hotsrm 行业扩展包

> 状态：**设计保留，未排期**（2026-10-23，[ADR-0009](../adr/0009-core-first-pack-criteria-and-customer-layer.md)）。
> 三个包的设计草案保留，v0.7 前不开发；第一个客户出现时按 §3.5 的准入标准决定做包还是进核心。
> 上位文档：[核心设计](../design/README.md)

## 1. 三层结构

hotsrm 面向不同行业的企业，但不为每个客户做一套系统。客户实际使用的版本由三层叠加而成：

| 层 | 内容 | 谁会用 | 放在哪里 |
|---|---|---|---|
| **通用核心** | 所有企业都需要的供应商管理功能与管理制度：供应商生命周期、合同、质量整改、绩效、风险、门户、寻源定价（27 个对象；订单到付款留在 ERP，[ADR-0008](../adr/0008-order-to-pay-stays-in-erp.md)） | 所有客户 | 设计在 `docs/design/`，源码在 `src/core/` |
| **行业扩展包** | 某一类企业共有的做法，作为模块在构建时合进应用；**现阶段只有设计** | 同类客户 | 设计在 `docs/packs/`；源码目录（`src/bulk/`、`src/hazmat/`、`src/soe/`）在立项时再建 |
| **客户层** | 某个客户的参数取值、组织结构、物资目录、审批岗位称谓、文件编号与样式、Studio 覆盖层（标签、必填、选项、新增字段、隐藏字段、视图、流程）、AI 生成的客户私有包 | 单个客户 | 客户的私有仓库与客户环境，**不进本仓库** |

客户提出一个新需求时，按下面的顺序决定它落在哪一层：

1. 别的客户也会需要吗？会 → 做进**通用核心**；
2. 同一类客户（同行业、同类物料、同类所有制）会需要吗？会，且满足 §3.5 的准入标准 → 做进**扩展包**；
3. 只是取值不同吗？是 → 做成**参数**，在客户层赋值；
4. 以上都不是 → 放**客户层**（Studio 覆盖层或客户私有包），不改核心源码。客户层的规则见 ADR-0009 第 4 条。

## 3. 扩展包怎么组合与安装

### 3.1 构建时合成一个应用

ObjectStack 的安装单位是**应用**（`type: app`）：客户安装、打开、卸载的都是一个应用；
其他类型的包（如 `type: module`）只能随应用一起交付，不能单独安装，应用之间的依赖目前
也不支持。所以扩展包**不是**装完核心之后再单独安装的东西，而是源码级的模块，在**构建
时**和核心合成一个应用（决策与依据见 [ADR-0002](../adr/0002-packs-composed-into-one-app.md)）：

| 源码目录 | 包类型 | 说明 |
|---|---|---|
| `src/core/` | `app` | 核心，也是应用的身份：客户安装的就是它 |
| `src/bulk/`、`src/hazmat/`、`src/soe/` | `module` | 三个扩展包（未建） |
| `src/bridges/<包A>-<包B>/` | `module` | 两个扩展包同时组合时才需要的联动（见 §3.3；暂不做） |

根目录的 `objectstack.composition.ts` 按扩展包开关选出要组合的模块，
`objectstack.config.ts` 把它们合成一个发布制品：

| 发行版 | 组合 | 在哪里组合 | 发布到 |
|---|---|---|---|
| 标准版 | 核心 | 本仓库 | 公开应用市场 |
| 客户版 | 核心 + 客户选定的扩展包 + 客户初始化数据 | 客户的私有仓库 | 只发布到该客户的组织 |

客户以后需要再加一个扩展包时，发布同一个应用的新版本（多组合一个模块），在环境里
升级即可：新增的对象和流程随升级加入，已有数据不受影响。**去掉一个扩展包等于删除对象
和数据，按「只加不减」处理**：用不到的功能用权限和停用流程关闭，不从发行版里移除。

### 3.2 扩展包怎么接入核心

扩展包不修改 `src/core/` 下的任何文件，只通过平台提供的三种扩展方式接入。按 ADR-0009
第 3 条收窄：包主要新增**自己的对象**；对核心对象的 `objectExtensions` 每个包不超过 2–3 个
字段，只放关联键和开关，业务字段放包自己的对象（否则核心对象在 Studio 里分成多层，客户
难以设计）。

| 方式 | 用途 | 例子 |
|---|---|---|
| `objectExtensions` | 给核心对象加字段、校验规则、索引 | 大宗物料包给采购订单加「来源」字段；国企采购合规包给寻源单加「采购方案」引用 |
| `picklistExtensions` | 给核心的共享选项列表追加选项 | 大宗物料包给对账明细类型加「大宗结算」；危化品包给风险类型加「安全事件」 |
| 导航贡献 | 把扩展包的菜单挂进核心应用的指定分组，没有对应对象时自动不显示 | 大宗物料包在「订单协同」分组下加「年度协议」「月度计划」「到货车次」 |

因此核心要为扩展预留位置：可能被扩展包追加选项的枚举，在核心里做成**共享选项列表**
（picklist），而不是写在字段上；核心应用的导航按分组组织，扩展包挂在分组下。

### 3.3 扩展包之间的联动：桥接模块

> 暂不做：两个包之间的联动等两个包都有客户时再设计（ADR-0009 第 3 条）。下面是设计基线。

两个扩展包同时组合时才有意义的联动（例如大宗物料包的到货车次关联危化品包的入厂预约），
不能写在任何一个包里，否则只组合其中一个包时会引用不存在的对象。这类联动放在
**桥接模块** `src/bridges/<包A>-<包B>/` 里，用 `objectExtensions` 给两边的对象加关联字段；
组合文件在两个包都被选中时自动带上对应的桥接模块。

### 3.4 每个扩展包包含什么

每个扩展包同时包含**系统部分**和**制度部分**：

| 组成 | 说明 |
|---|---|
| 对象与字段 | 扩展包新增自己的对象，命名为 `srm_<包前缀>_*`（大宗物料包 `srm_bulk_`、危化品包 `srm_hz_`、国企采购合规包 `srm_soe_`），通过 `lookup` 关联核心对象 |
| 对核心的扩展 | 只用 §3.2 的三种方式 |
| 流程与自动化 | 扩展包自己的 flow、审批、screen flow；与核心流程衔接的地方写明触发点 |
| 权限 | 扩展包自己的权限集；面向供应商的对象沿用核心的门户隔离方式（`portal_position`，见[核心 04 §3](../design/04-security-and-portal.md#3-供应商门户的数据隔离)） |
| 参数 | 扩展包在 `params/<包>.yaml` 声明自己的参数及示例默认值；客户在私有配置里赋值 |
| 体系文件模板 | 扩展包对应的管理办法与表单模板，放在 `governance/templates/<包>/`，见 [体系文件](../../governance/README.md) |
| 集成 | 扩展包需要的外部系统接口（如地磅、化验系统、电子招标平台） |

### 3.5 准入标准与依赖顺序

满足任一条件才立项为扩展包（ADR-0009 第 2 条）：受法规约束、有明确合规要求；三家以上
客户复用同一套做法；需要保护专门的测试资产。只是一家客户的做法，放客户层。

| 包 | 依赖 | 可立项时点 |
|---|---|---|
| 国企采购合规包 | 核心寻源（v0.7）与合同（v0.3） | v0.7 之后最早可做；受法规约束，满足准入标准 |
| 大宗物料包 | 订单、收货、结算（都在 ERP），需要 ERP 集成和门户镜像 | ERP 集成落地之后；月度订单 SRM → ERP 的反向数据流（I9b）要先补进 06 §1.2 |
| 危化品包 | 入厂预约依赖订单镜像；承运商、许可范围只依赖核心供应商 | 承运商与许可部分可在 ERP 集成前做，预约部分在 ERP 集成之后 |

组合构建测试在第二个包出现时才加入 CI，在此之前按单个应用开发。

## 4. 编写约定

- **不写客户名，也不写能认出客户的组合**：示例用行业通行做法，不照搬某个客户的物料
  清单、组织形态或合同条款。
- **参数给示例值并标明「示例」**：不使用任何客户的实际取值。
- **引用法规写名称，不抄全文**：具体适用以现行法规和客户法务意见为准。
- **与核心一致**：沿用核心的建模原则（[核心 02 §1](../design/02-domain-model.md#1-建模原则)）和
  声明式优先的约束（[核心 03 §2](../design/03-processes-and-automation.md#2-平台机制与本设计的用法)）。
