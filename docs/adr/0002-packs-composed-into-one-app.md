# ADR-0002：扩展包在构建时与核心合成一个应用

- 状态：已采纳
- 日期：2026-10-22

## 背景

hotsrm 由通用核心和三个行业扩展包组成（大宗物料、危化品、国企采购合规），不同客户需要
不同的组合。最初的设想是「每个扩展包是依赖核心的独立应用，装完核心再按需安装」，核对
ObjectStack 的规定后发现这条路走不通：

- **安装单位是应用**：客户安装、打开、卸载的只有 `type: app` 的包；`module` 等类型只能
  随应用一起交付，不能单独安装（ObjectStack [ADR-0019](https://github.com/objectstack-ai/objectstack/blob/main/docs/adr/0019-app-as-consumer-unit.md) D1–D3）。
- **应用之间的依赖目前不支持**：ADR-0019 把「应用之间的依赖与共享数据模型」列为有意
  推迟的事项。
- **一个制品可以带多个包**（ObjectStack [ADR-0130](https://github.com/objectstack-ai/objectstack/blob/main/docs/adr/0130-release-artifact-as-co-ownership-boundary.md)）：一个 `app` 加若干 `module`，
  一次安装、一次卸载。官方的 [HotCRM](https://github.com/objectstack-ai/hotcrm) 就是这样组织的。
- 托管云的发布入口目前只接受单包（扁平）制品，多包制品要先合并成一个包再发布。
- 平台提供三种跨包扩展方式：`objectExtensions`（给别的包的对象加字段、校验、索引）、
  `picklistExtensions`（给别的包的共享选项列表追加选项）、导航贡献（往别的应用的导航
  分组挂菜单）。

## 决定

- **源码按模块组织**：`src/core/`（`type: app`）、`src/bulk/`、`src/hazmat/`、`src/soe/`
  （`type: module`），以及两个扩展包同时组合时才需要的桥接模块 `src/bridges/<A>-<B>/`。
- **构建时组合**：根目录的 `objectstack.composition.ts` 按扩展包开关选出模块（两个扩展包
  都选中时自动带上对应桥接模块），`objectstack.config.ts` 把它们合成一个应用。制品用多包
  形式还是合并成单包，按发布目标当时支持的方式选，源码结构不受影响。
- **发行版**：标准版只含核心，在本仓库构建，发布到公开市场；客户版在客户的私有仓库里
  组合（核心 + 选定扩展包 + 客户初始化数据），只发布到该客户的组织。
- **扩展包只能用三种扩展方式接入核心**，不修改 `src/core/`；扩展包之间不互相引用，联动
  放桥接模块。核心为此预留位置：可扩展的枚举做成共享选项列表，导航按分组组织。
- **只加不减**：客户以后加扩展包，就是发布同一应用的新版本并升级；不从已上线的发行版里
  移除扩展包，用不到的功能用权限和停用流程关闭。

## 考虑过的方案

| 方案 | 为什么没选 |
|---|---|
| 每个扩展包是独立应用，依赖核心应用 | 平台不支持应用之间的依赖；即使技术上能装上，卸载顺序、升级兼容都没有保障 |
| 所有扩展包永远打进同一个应用，靠开关启用 | 每个客户都会带上用不到的对象和流程；开关只能隐藏，不能去掉表和数据 |
| 每种组合做一个独立应用，各有各的标识 | 同一客户从一种组合换到另一种时，应用标识变了，无法原地升级 |

## 后果

- 客户只看到一个应用，安装、升级、卸载都是一次完成。
- 每种组合都必须能构建并通过校验：测试里要覆盖「只有核心」「核心 + 单个扩展包」「核心 +
  全部扩展包」等组合。
- 去掉扩展包会删除对象和数据，平台目前也没有带数据的元数据迁移，所以「只加不减」是硬
  规则。

## 待验证

- 同一个应用升级到新版本时新增一批对象（加入一个扩展包），在托管云上的升级是否顺畅。
- 客户版用托管安装（定义锁定，可升级）还是模板安装（复制一份，完全可改，但以后不能升级）。
  倾向托管安装，保住升级能力。
