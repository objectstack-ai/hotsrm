# ADR-0005：体系文件与系统共用一份参数，源文件用 Markdown

- 状态：已采纳
- 日期：2026-10-22

## 背景

客户上 SRM 前，通常会要求先把供应商管理制度（体系文件）定下来。制度和系统里有大量相同
的参数：审批金额档、整改时限、绩效等级线、证书提醒天数等。如果制度用 Word 单独维护、
系统另行配置，两边很快会不一致，内审和外审都会开不符合项。Word 作为源文件还有两个
问题：改了什么很难逐字对比；每个客户一套，无法复用。

## 决定

- **参数只维护一处**：参数定义和示例默认值放在仓库根目录的 `params/`（核心与每个扩展包
  各一个文件）。体系文件生成脚本和应用包构建都读它。
- **模板用 Markdown**：通用模板放在 `governance/templates/`，用 `{{param.*}}` 引用参数，
  `{{org.*}}` 引用客户组织信息，`<!-- pack:<包名> -->` 标记只在组合了某扩展包时保留的
  段落。
- **客户实例放客户私有仓库**：参数取值、组织信息、专属段落、Word 样式模板和生成的
  交付物都不进本仓库。
- **交付物是生成的 Word / PDF**：客户在 Word 里评审批注，意见由实施顾问合并回源文件后
  重新生成；定稿签批后的 PDF 或 Word 是受控版本。
- **条款与控制点对应**：制度里写「在 SRM 系统中执行」的要求，系统必须有对应控制；系统
  里的强制控制都能在制度里找到条款。

## 考虑过的方案

| 方案 | 为什么没选 |
|---|---|
| Word 作为源文件 | 无法逐字对比版本；参数在多份文件和系统里重复；每个客户复制一套，无法复用 |
| 在线协作文档作为源文件 | 适合评审讨论，但没有参数和条件段落，不能由同一份源生成多个客户的版本 |

## 后果

- 需要一套生成脚本：填参数、处理条件段落、按客户样式用 pandoc 生成 Word、填文件控制表。
- 改参数要同时影响制度和系统，参数文件的改动按代码一样走评审。
- 客户的体系工程师不需要接触 Markdown 或 git，只在 Word 上工作。
