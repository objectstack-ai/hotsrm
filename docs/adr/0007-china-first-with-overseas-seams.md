# ADR-0007：中国优先，为出海留三个口子

- 状态：已采纳
- 日期：2026-10-23

## 背景

- hotsrm 的客户和近期的潜在客户都是中国企业。核心设计已经按中国企业的做法编写：增值税
  专票和数电票、统一社会信用代码、工商信息核验，扩展包里还有国企采购合规包。
- 曾考虑「从第一天就国际通用，中国作为本地化包」。代价有三：每个设计都要多判断一次
  「这是核心还是本地化」；要维护「不装中国本地化」的构建组合，却没有国际客户来验证它；
  国际版的法规内容（美国内控法规、欧盟和德国的供应链尽职调查法规、反贿赂法、欧盟数据
  保护、制裁筛查）需要重写，不是翻译。
- 体系文件本身是本地化的。以一套按本仓库模板编写的客户体系文件（约 18 份）统计：直接
  引用约 13 部中国法规；中国特有的做法出现得更多，例如营业执照和统一社会信用代码 23 处、
  许可证 38 处、安全生产 19 处、纪检 17 处、失信和信用公示 13 处、招标投标 8 处。
- 国际需求最可能来自中国客户自己的海外工厂（东南亚、墨西哥、欧洲）：管理当地供应商，
  需要当地币种、当地语言、当地税号。
- 现有设计有一处自相矛盾：统一社会信用代码是供应商的必填唯一字段（[02 §4.1](../design/02-domain-model.md#41-供应商主数据)），
  境外供应商因此建不了档；而默认画像又写着「少量外资供应商需英文界面」（[设计总览 §3](../design/README.md#3-默认业务画像设计假设)）。
- 平台约定：元数据里写的标签就是部署默认语言的文字，其他语言由翻译包提供；
  `os i18n check` 可以检查翻译覆盖率，并可作为 CI 关卡。

## 决定

**中国优先，为出海留三个口子。**

1. **中国优先**：默认语言、默认参数、流程、演示数据、文档都按中国企业编写。中国特有的
   做法直接做进核心或对应的扩展包，不为「通用」做抽象。
2. **三个口子**，现在就做，因为以后补的代价大：

   | 口子 | 要求 | 现状 |
   |---|---|---|
   | 金额带币种 | 报价、订单、对账等金额字段都带 `currency` | 已有 |
   | 中英双语 | 标签用中文写；英文翻译覆盖**全部**对象、字段、选项、视图和通知模板，不只门户对象；翻译缺失时构建失败 | 原规定只要求门户对象补英文，本记录扩大到全部 |
   | 供应商标识按国家 / 地区区分 | 供应商和准入申请增加 `country`（默认 `cn`）；统一社会信用代码只对中国供应商必填并校验格式；境外供应商填当地注册号或税号 `registration_no`；查重和黑名单按身份标识判断：境内用统一社会信用代码，境外用「国家 / 地区 + 注册号」 | 本记录新增 |

3. **体系文件做中国版，对标国际**：
   - 正文按中国法规和中国企业的做法编写；ISO 9001、ISO 20400、COSO 内部控制框架、联合国
     全球契约、国际劳工组织公约、RBA 行为准则等国际框架作为对标依据。
   - 法规和标准的名称集中写在每份文件的「引用文件」一节；条款只写要求，需要时
     引用该节。
   - 资质名称（营业执照、各类许可证）放进资质清单数据（物资分类与资质的对照表），条款
     写「按资质清单」，不在条款里逐一列举。
4. **不做**：国际法规内容、英文版文档和演示数据、税务和电子发票的通用抽象、「不装中国
   本地化」的构建组合。出现第一家要在海外工厂使用的客户时，再按国家加扩展包（`type:
   module`，接入方式同 [ADR-0002](./0002-packs-composed-into-one-app.md)）。

## 考虑过的方案

| 方案 | 为什么没选 |
|---|---|
| 国际通用为核心，中国作为本地化包 | 没有国际客户验证，抽象只能靠猜；每个设计多一道判断；要维护一个没人用的构建组合；国际法规内容要重写 |
| 只做中国，不留口子 | 统一社会信用代码必填会挡住境外供应商，这在国内企业就会遇到（进口物料、外资供应商）；标签不补英文，海外工厂的员工和供应商用不了；以后再补要迁移数据 |

## 后果

- 设计文档同步修改：[01](../design/01-requirements.md) FR-102、FR-203、BR-01、BR-02 和非功能需求「国际化」；
  [02](../design/02-domain-model.md) §4.1 供应商、§4.2 准入申请、§7 元数据示例；[03](../design/03-processes-and-automation.md) 受理查重；
  [04](../design/04-security-and-portal.md) 门户字段规则；[05](../design/05-experience-and-analytics.md) §6 多语言；[06](../design/06-integration-and-ai.md) 企业信息服务；[设计总览](../design/README.md)默认画像。
- [AGENTS.md](../../AGENTS.md) 增加两条规则：英文翻译覆盖全部元数据；体系文件模板的法规名称
  集中在「引用文件」、资质名称走资质清单。
- CI 用 `os i18n check --strict` 检查英文翻译：非默认语言缺少词条即报错；平台自带的
  词条默认不计入本应用的覆盖率。
- 同一个环境同时安装标签用英文写的应用（如 hotcrm）和本应用时，两边都靠完整的翻译包
  显示同一种语言；环境的默认语言设为客户的主要语言。
- 统一社会信用代码的外部核验（工商信息服务）只适用于中国供应商；境外供应商先人工核验，
  有需要时再接境外企业信息服务。

## 待验证

- **空值与唯一约束**：`credit_code` 字段唯一，以及 `country` + `registration_no` 组合唯一时，
  多条空值在各数据库上的表现不同（PostgreSQL 允许多个空值，SQL Server 的唯一约束只允许
  一个空值）。实现前以平台实测为准，必要时改为只对非空值生效的约束。
  - 结果（2026-10-23）：平台提供空值安全的租户内唯一索引（objectstack ADR-0120，
    `nullSafeColumns`）；v0.1 实现分支（PR #5）两条境外供应商 `credit_code` 均为空且
    测试通过（内存库）。PostgreSQL / SQL Server 上的表现在 v0.1 上生产前实测（07 §6 V8）。

## 补充说明（2026-10-23）

- 中国特有字段在对象里单独分组（供应商的「工商与税务」：统一社会信用代码、纳税人
  类型等），证书类型里的中国资质（生产许可、3C）保留在共享选项列表。出现第一家全球
  客户时，可按边界评估 §8 的清单拆成中国本地化包（[ADR-0009](./0009-core-first-pack-criteria-and-customer-layer.md) 第 6 条）。
- 核心的源语言（中文源英文译，还是英文源中文译）在 v0.3 前单独决定（计划 D4）。
  - 结果（2026-10-24）：**中文源、英文译**，即维持本记录「标签用中文写」的做法。理由：
    准入、会签、试供、否决项这类术语由中文体系文件定义，体系文件受中国法规约束、
    与系统共用措辞（[ADR-0005](./0005-governance-and-system-share-parameters.md)），
    中文为源最不易走样；对象名、字段名、API 本来就是英文，源语言只影响界面文字；
    英文翻译强制全覆盖后，两种语言的界面效果一致。若将来要把 hotsrm 作为面向海外
    用户的通用模板，再做一次「标签 ↔ 翻译」的机械对调即可，不改 API 名，门槛 2 之前
    随时可做。
